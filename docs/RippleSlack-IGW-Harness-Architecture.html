Ripple Slack → AgentCore: Full Architecture with Ingress Gateway + Harness

Path A Primary: Slack → Ingress GW → Runtime (delegation + consent)    Path B Exploratory: Slack → Ingress GW → Harness (consent only, no delegation)

Numbered Data Flow

1User asks question in Slack — already authenticated via Okta SSO to workspace. No login prompt.
2Slack delivers event payload — HTTP POST with user_id, team_id, message. Signed by Slack.
3Verify Slack request signature — HMAC-SHA256 against Slack signing secret. Confirms authenticity.
4Resolve identity + mint JWT — maps user_id → email, signs JWT with sub=user@ripple.com, aud=agentcore.
5POST to Ingress Gateway — Authorization: Bearer <jwt>. Same shape as client/ask.py today.
6Ingress GW validates JWT — CUSTOM_JWT authorizer checks signature via JWKS, verifies iss + aud.
7aPath A → Runtime — JWT_PASSTHROUGH forwards the original JWT unchanged. Runtime's own authorizer validates again. Your primary path — supports both M1+M2.
7bPath B → Harness (exploratory) — routes to managed harness target. ⚠️ No RequestHeaderConfiguration — caller JWT not visible to tools. M2 delegation impossible.
8agent.py → identity_claims.py — re-verifies JWT signature, checks email_verified, domain allowlist. Three fail-closed gates.
9Dispatch gdrive_tool (M2) — uses verified_email() as assertion subject. Google mints token scoped to ONE user. Only on Path A.
10github_tool → Tools Gateway — agent calls through MCP gateway. Gateway holds the user's vaulted OAuth token (M1 consent).
11Harness → Tools Gateway — managed loop calls tools via gateway with OAUTH (client_credentials). GitHub works; Drive doesn't (shared identity, not per-user).
12Google Drive API — direct call with domain-wide delegation assertion. Drive trims results to that user's files. Path A only.
13GitHub API — Tools GW resolves per-user vaulted token, calls GitHub. GitHub returns only repos/files that user can access.
14Response returns — answer + citations + confidence band flows back through Ingress GW to Ripple middleware.
15Post to Slack — chat.postMessage sends formatted answer back to the user's DM or thread.
Key architectural insight — why both paths exist:

Path A (Runtime) is the primary path and MUST stay. It's the only path where identity_claims.py can read the JWT from the request header and use verified_email() for Google Drive domain-wide delegation (M2). The Ingress Gateway's JWT_PASSTHROUGH is what makes this possible — it forwards the JWT unchanged so agent.py can re-verify it.

Path B (Harness) is additive / exploratory. The managed harness has no RequestHeaderConfiguration, so it cannot see the caller's JWT. It can only reach sources through the Tools Gateway using machine-identity OAuth (client_credentials). This means:
  • ✅ GitHub works — Tools GW handles per-user token vault + consent (M1)
  • ❌ Google Drive does NOT work — needs per-user email for assertion subject; harness can't provide it
  • ⚠️ Shared identity risk — without per-user JWT pass-through, all harness calls appear as one machine identity

What changes from adding Slack: Only the caller identity — from Auth0 (device-code flow) to your Slack middleware. The Ingress Gateway's CUSTOM_JWT authorizer trusts both issuers, so CLI and Slack coexist. Everything inside the AgentCore boundary (steps 6–14) is unchanged.
